## 📌 مقدمه: چرا نیازمندی‌ها را مدلسازی می‌کنیم؟

در فصل ۷ دیدیم که نیازمندی‌ها را چگونه استخراج کنیم. اما متن‌های طولانی و توضیحات شفاهی معمولاً دچار **ابهام، تناقض و برداشت‌های متفاوت** می‌شوند.  
**مدلسازی تحلیل (Analysis Modeling)** پل ارتباطی میان «استخراج نیازمندی متنی» و «طراحی معماری نرم‌افزار» است.

### 🎯 اهداف اصلی مدلسازی نیازمندی‌ها:
1. **توصیف دقیق آنچه مشتری می‌خواهد:** بدون درگیر شدن با جزئیات فنی کدنویسی.
2. **ایجاد پایه‌ای برای طراحی نرم‌افزار:** طراحان معماری مستقیماً از روی این مدل‌ها ساختار کد را می‌سازند.
3. **تعریف ملاک‌های اعتبارسنجی و تست:** تیم تست از روی این دیاگرام‌ها سناریوهای تست را طراحی می‌کند.

---

## 💡 ۳ اصل طلایی در مدلسازی نیازمندی‌ها (Rules of Thumb)

۱. **بر دامنه مسئله تمرکز کنید، نه راهکار فنی:** مدل باید نشان دهد سیستم *چه کاری* انجام می‌دهد (What)، نه اینکه با چه زبان یا دیتابیسی پیاده می‌شود (How).  
۲. **مدل را تا جای ممکن ساده نگه دارید:** پیچیدگی اضافه باعث سردرگمی مشتری و تیم توسعه می‌شود.  
۳. **جزئیات غیرضروری را به فاز طراحی موکول کنید:** در این فاز نیازی نیست جنس متغیرها یا توابع داخلی دقیقاً مشخص شوند.

# بخش ۱: مدلسازی سناریومحور (Scenario-Based Modeling)

مدلسازی سناریومحور، سیستم را از **نگاه کاربران (Actors)** توصیف می‌کند و نشان می‌دهد سیستم در قالب سناریوهای واقعی چه رفتاری دارد.

---

### ۱.۱. نمودار Use Case در زبان UML

نمودار Use Case نقش‌ها (Actors) و قابلیت‌های اصلی سیستم (Use Cases) را همراه با روابط بین آن‌ها نشان می‌دهد.

#### عناصر اصلی:
* **آکتور (Actor):** موجودیت خارجی (انسان، سیستم دیگر یا زمان) که با سیستم تعامل دارد.
* **یوزکیس (Use Case):** یک جریان کاری کامل که ارزشی ملموس برای آکتور تولید می‌کند.

#### روابط مهم در Use Caseها:
* **رابطه `<<include>>` (الزامی):** وقتی یک یوزکیس *همیشه* بخش مشترکی از یوزکیس دیگر را فراخوانی می‌کند.
  * *مثال:* یوزکیس «ثبت درخواست رزرو» **همیشه** یوزکیس «احراز هویت کاربر» را `<<include>>` می‌کند.
* **رابطه `<<extend>>` (اختیاری/شرطی):** وقتی یک یوزکیس تحت شرایط خاصی به یوزکیس اصلی اضافه می‌شود.
  * *مثال:* یوزکیس «محاسبه جریمه دیرکرد» فقط در صورت تاخیر کاربر، یوزکیس «تحویل تجهیزات» را `<<extend>>` می‌کند.

---

### ۱.۲. نمودار فعالیت (Activity Diagram) و مسکوب‌های شناوری (Swimlanes)

نمودار فعالیت مانند یک فلوچارت پیشرفته است که جریان کاری (Workflow) یک سناریو را گام‌به‌گام نشان می‌دهد.

#### خطوط شناوری (Swimlanes):
وقتی بخواهیم مشخص کنیم **چه کسی یا چه بخشی** مسئول انجام هر گام از فعالیت است، نمودار را به ستون‌های عمودی به نام Swimlanes تقسیم می‌کنیم.

#### 🏢 مثال پروژه آزمایشگاه: نمودار فعالیت «فرآیند رزرو و تحویل قطعه» با Swimlanes

```
┌──────────────────┬──────────────────────────┬──────────────────────────┐
│  دانشجو (Student) │  سیستم (System Engine)   │ اپراتور (Lab Operator)   │
├──────────────────┼──────────────────────────┼──────────────────────────┤
│ 1. انتخاب قطعه   │                          │                          │
│    و زمان رزرو   │                          │                          │
│       │          │                          │                          │
│       ▼          │                          │                          │
│                  │ 2. بررسی موجودی قطعه     │                          │
│                  │    در تاریخ درخواستی      │                          │
│                  │       │                  │                          │
│                  │       ├──► [ناموجود] ──► اعلام خطا به دانشجو        │
│                  │       │                  │                          │
│                  │       ▼ [موجود]          │                          │
│                  │ 3. ایجاد درخواست معلق    │                          │
│                  │       │                  │                          │
│                  │       └─────────────────►│ 4. بررسی و تایید/رد      │
│                  │                          │    درخواست رزرو          │
│                  │                          │       │                  │
│                  │ 5. ثبت نهایی رزرو و     │◄──────┘                  │
│                  │    ارسال پیامک تایید      │                          │
└──────────────────┴──────────────────────────┴──────────────────────────┘
```

# بخش ۲: مدلسازی کلاس‌محور (Class-Based Modeling)

مدلسازی کلاس‌محور، ساختار ایستا (Static Structure) سیستم را نشان می‌دهد؛ یعنی چه **اشیائی** در سیستم وجود دارند و چه ارتباطی با هم دارند.

---

### ۲.۱. روش شناسایی کلاس‌های تحلیل (Grammatical Parse)

یکی از ساده‌ترین روش‌های استخراج کلاس‌ها از روی متن سناریوها، **تحلیل نحوی (Grammatical Parse)** است:
* **اسم‌ها (Nouns) ──► کلاس‌های پیشنهادی** (مثل: دانشجو، وسیله، برگه رزرو، اپراتور).
* **افعال (Verbs) ──► متدها/عملیات‌ها** (مثل: ثبت کردن، تایید کردن، محاسبه جریمه).

---

### ۲.۲. دسته‌بندی ۳ گانه کلاس‌های تحلیل

پرسمن کلاس‌های تحلیل را به ۳ دسته کلیدی تقسیم می‌کند:

۱. **کلاس‌های موجودیت (Entity Classes):** داده‌ها و اطلاعات ماندگار سیستم را نگهداری می‌کنند. (مثال: `Equipment` ، `BorrowRequest` ، `User`).  
۲. **کلاس‌های مرزی (Boundary Classes):** واسط میان سیستم و دنیای بیرون (کاربران یا سیستم‌های دیگر) هستند. (مثال: `ReservationFormUI` ، `SmsGatewayNotifier`).  
۳. **کلاس‌های کنترلی (Control Classes):** منطق کسب‌وکار (Business Logic) و هماهنگی بین کلاس‌های دیگر را مدیریت می‌کنند. (مثال: `FineCalculationManager` ، `ReservationController`).

---

### ۲.۳. کارت‌های CRC (Class-Responsibility-Collaborator)

کارت CRC یک ابزار فیزیکی یا مفهومی ساده برای جلسات طوفان فکری تیم توسعه است. هر کارت ۳ بخش دارد:
1. **Class Name:** نام کلاس.
2. **Responsibilities:** مسئولیت‌ها و کارهایی که این کلاس باید بداند یا انجام دهد.
3. **Collaborators:** کلاس‌های دیگری که این کلاس برای انجام وظایفش به آن‌ها نیاز دارد.

#### 🟨 نمونه کارت CRC برای سیستم آزمایشگاه:

| Class Name: `BorrowRequest` (درخواست امانت) | |
| :--- | :--- |
| **Responsibilities (مسئولیت‌ها):** | **Collaborators (همکاران):** |
| - نگهداری تاریخ رفت و برگرداندن قطعه | `User` (متقاضی) |
| - محاسبه تعداد روزهای تاخیر | `Equipment` (قطعه درخواستی) |
| - بررسی صحت تاریخ‌های رزرو | `PenaltyCalculator` (محاسبه‌گر جریمه) |

---

### ۲.۴. نمودار کلاس (Class Diagram) در UML

نمودار کلاس، کلاس‌ها، ویژگی‌ها (Attributes)، متدها (Operations) و روابط بین آن‌ها را نمایش می‌دهد.

#### انواع روابط بین کلاس‌ها:
* **ارتباط ساده (Association):** ارتباط دوطرفه یا یک‌طرفه معمولی بین دو کلاس.
* **تجميع (Aggregation - رابطه کل و جزء ضعیف):** کلاس جزء می‌تواند بدون کلاس کل هم وجود داشته باشد. (با لوزی توخالی `◇` نشان داده می‌شود).
  * *مثال:* رابطه بین `Laboratory` و `Equipment` (اگر آزمایشگاه تعطیل شود، تجهیزات هنوز وجود دارند).
* **ترکیب (Composition - رابطه کل و جزء قوی):** اگر کلاس کل نابود شود، جزء هم نابود می‌شود. (با لوزی پر `◆` نشان داده می‌شود).
  * *مثال:* رابطه بین `BorrowRequest` و `PenaltyReceipt` (رسید جریمه بدون خود درخواست معنی ندارد).
* **چندتایی (Multiplicity):** نشان‌دهنده تعداد اشیاء در رابطه است (`1` ، `*` ، `0..1`).

#### 📐 دیاگرام کلاس ساده سیستم مدیریت لوازم آزمایشگاه:

```
┌─────────────────────────┐               ┌─────────────────────────┐
│          User           │ 1           * │      BorrowRequest      │
├─────────────────────────┤───────────────├─────────────────────────┤
│ - userId: string        │  registers    │ - requestId: string     │
│ - fullName: string      │               │ - startDate: DateTime   │
│ - userRole: UserRole    │               │ - returnDate: DateTime  │
├─────────────────────────┤               │ - status: RequestStatus │
│ + createRequest()       │               ├─────────────────────────┤
└─────────────────────────┘               │ + calculateDelayDays()  │
                                          └───────────┬─────────────┘
                                                      │ *
                                                      │
                                                      │ is for
                                                      │
                                                      │ 1
                                          ┌───────────┴─────────────┐
                                          │        Equipment        │
                                          ├─────────────────────────┤
                                          │ - equipmentId: string   │
                                          │ - name: string          │
                                          │ - dailyFineRate: decimal│
                                          │ - isAvailable: bool     │
                                          ├─────────────────────────┤
                                          │ + updateStatus()        │
                                          └─────────────────────────┘
```

# بخش ۳: مدلسازی رفتاری (Behavioral Modeling)

مدلسازی رفتاری، **تغییرات سیستم در طول زمان** و واکنش آن به **رویدادهای خارجی (Events)** را توصیف می‌کند.

---

### ۳.۱. نمودار ماشین حالت (Statechart / State Diagram)

این نمودار چرخه حیات (Lifecycle) یک شیء و حالت‌های مختلفی که در اثر رویدادها پذیرد را نشان می‌دهد.

#### مفاهیم کلیدی:
* **حالت (State):** وضعیتی که شیء در آن قرار دارد و منتظر یک رویداد است.
* **رویداد (Event):** اتفاقی که باعث تغییر حالت می‌شود.
* **انتقال (Transition):** حرکت از یک حالت به حالت دیگر.

#### 🔄 نمودار حالت یک «وسیله آزمایشگاهی» (Equipment Lifecycle):

```
       [شروع]
          │
          ▼
    ┌───────────┐  رزرو توسط دانشجو   ┌───────────┐
    │ Available │───────────────────►│ Reserved  │
    │ (موجود)   │◄───────────────────│ (رزرو شده)│
    └───────────┘    لغو رزرو        └─────┬─────┘
          ▲                                │
          │                                │ تحویل قطعه به کاربر
          │ تحویل قطعه به آزمایشگاه        ▼
          │                          ┌───────────┐
          └──────────────────────────│   InUse   │
                                     │ (در دست)  │
                                     └─────┬─────┘
                                           │
                                           │ خرابی قطعه
                                           ▼
                                     ┌───────────┐
                                     │Maintenance│
                                     │(در تعمیر) │
                                     └───────────┘
```

---

### ۳.۲. نمودار توالی (Sequence Diagram)

نمودار توالی نشان می‌دهد که اشیای مختلف سیستم **به ترتیب زمان (Chronological Order)** چگونه با ارسال پیام (Message) با یکدیگر تعامل می‌کنند.

* **خط عمودی (Lifeline):** طول عمر شیء را در زمان نشان می‌دهد.
* **کادرهای مستطیلی روی خط (Activation Box):** زمانی که شیء در حال پردازش است.

# بخش ۴: الگوهای تحلیل و مدلسازی چابک

### ۴.۱. الگوهای تحلیل (Analysis Patterns)
الگوهای تحلیل، راهکارهای بازاستفاده‌پذیر (Reusable) برای مسائل تکراری در فاز تحلیل هستند.  
*مثال:* الگوی **Party-Role** یک الگوی تحلیل معروف است که برای مدیریت نقش‌های مختلف افراد (دانشجو، استاد، اپراتور) در سیستم‌ها استفاده می‌شود.

### ۴.۲. مدلسازی چابک (Agile Modeling)
در روش‌های چابک (مثل اسکرام)، مدلسازی تعطیل نمی‌شود، بلکه **سبک و کاربردی** انجام می‌شود:
* دیاگرام‌ها روی **تخته وایت‌برد** رسم می‌شوند.
* فقط به اندازه‌ای مدل می‌کشیم که فهم مشترک حاصل شود (**Just Enough Modeling**).
* از ابزارهای سنگین CASE زودهنگام استفاده نمی‌کنیم.

# 🎯 نمونه سوالات امتحانی فصل ۸ (همراه با پاسخ تشریحی)

#### **سوال ۱:** تفاوت اصلی رابطه `<<include>>` و `<<extend>>` در نمودار Use Case چیست؟ با یک مثال از سیستم امانت آزمایشگاه توضیح دهید.
* **پاسخ:**  
  * **رابطه `<<include>>`:** نشان‌دهنده یک فراخوانی **همیشگی و الزامی** است. (مثال: یوزکیس «ثبت رزرو» همیشه یوزکیس «بررسی موجودی تجهیزات» را include می‌کند).
  * **رابطه `<<extend>>`:** نشان‌دهنده یک رفتار **اختیاری و شرطی** است که تحت شرایط خاص اضافه می‌شود. (مثال: یوزکیس «تحویل قطعه» تنها در صورت وجود تاخیر، یوزکیس «محاسبه جریمه» را extend می‌کند).

#### **سوال ۲:** انواع کلاس‌های تحلیل (Entity، Boundary، Control) را تعریف کرده و برای سیستم آزمایشگاه برای هر کدام یک نمونه نام ببرید.
* **پاسخ:**
  * **کلاس موجودیت (Entity):** نگهداری داده‌های ماندگار سیستم. (نمونه: کلاس `Equipment`).
  * **کلاس مرزی (Boundary):** واسط کاربر یا سیستم‌های خارجی. (نمونه: کلاس `ReservationUI`).
  * **کلاس کنترلی (Control):** مدیریت منطق محاسباتی و هماهنگی. (نمونه: کلاس `FineManager`).

#### **سوال ۳:** کارت CRC چیست و ۳ بخش اصلی آن کدامند؟
* **پاسخ:**  
  کارت CRC یک ابزار مدلسازی کلاس‌محور است که ۳ بخش دارد:  
  ۱. **Class Name (نام کلاس)**  
  ۲. **Responsibilities (مسئولیت‌های کلاس)**  
  ۳. **Collaborators (کلاس‌های همکار برای انجام مسئولیت)**

#### **سوال ۴:** نمودار ماشین حالت (Statechart) چه ابعادی از سیستم را مدلسازی می‌کند؟
* **پاسخ:**  
  این نمودار رفتار پویا و چرخه حیات یک شیء خاص را بر اساس **حالت‌ها (States)** و **رویدادهای خارجی (Events)** در طول زمان مدلسازی می‌کند.

## 📝 تکلیف پروژه‌ای جلسه آینده (جهت کامیت در گیتهاب)

هر دانشجو/تیم باید برای پروژه انتخابی خود، فایل `MODELING.md` را در ریپازیتوری گیتهاب ایجاد کرده و موارد زیر را در آن قرار دهد:

1. **یک نمودار Use Case کامل** شامل حداقل ۱ رابطه `<<include>>` و ۱ رابطه `<<extend>>`.
2. **یک نمودار فعالیت (Activity Diagram)** دارای Swimlanes برای فرآیند اصلی سیستم.
3. **طراحی ۲ کارت CRC** برای دو کلاس اصلی سیستم.
4. **یک نمودار ماشین حالت (Statechart Diagram)** برای چرخه حیات مهم‌ترین موجودیت سیستم.
